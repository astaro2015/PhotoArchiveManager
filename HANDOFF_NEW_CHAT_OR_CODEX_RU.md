# Photo Archive Manager — передача проекта в новый чат / Codex

### 1.15.3 — release-hardening и единая runtime-версия
Финальный аудит 1.15.2 закрыл два класса проблем: runtime-номер версии теперь берётся из assembly metadata, а Quarantine/direct-delete проверяют source-root и reparse points до физической операции; создаваемый путь карантина также проверяется до переноса. Release build компилируется с TreatWarningsAsErrors. SQLite schema остаётся 20, QualityAlgorithmVersion=6.

### 1.15.2 — события можно объединять drag&drop
Событие в дереве можно перетащить на другое событие: source поглощается target, имя target сохраняется, его обложка имеет приоритет, после merge выбран target. Обычный picker «Объединить…» приведён к той же семантике и больше не предлагает отдельное итоговое имя. Перенос отдельных фото drag&drop сохранён. Merge/move инвалидируют Organization Preview. Schema остаётся 20.

### 1.15.1 — после переноса лица остаёмся в исходной группе
Назначение лица другой группе через picker или drag&drop больше не переключает интерфейс на целевую группу. `LoadPeopleAsync` сохраняет текущую исходную группу по Id и перечитывает её лица; fallback используется только если исходная группа стала пустой и исчезла. Schema остаётся 20.

### 1.15.0 — единая отметка карантина для визуальных групп и серий
В «Похожие / копии» и «Серии» удалена двойная семантика `Оставить` + `в карантин`: единственная пользовательская галка — `в карантин`, всё неотмеченное остаётся. QuarantineService сам выводит keepers как дополнение к кандидатам и не позволяет убрать всю группу/серию. В серии рекомендация ставит quarantine-галки на нерекомендованные кадры. Schema остаётся 20.

### 1.14.9 — закрытие источника и карантин
Активный Quarantine больше не считается незавершённой операцией и не блокирует закрытие/удаление источника из PAM. При очистке каталога quarantine/audit строки сохраняются скрытыми; Undo закрытого источника возвращает файл на диск, но не активирует его в текущей библиотеке до повторного добавления source root. Schema остаётся 20.

## Что это за проект

Photo Archive Manager (PAM) — локальная Windows-программа для разбора большого семейного фотоархива.

Технологии:
- C#;
- .NET 8;
- WPF;
- SQLite (`Microsoft.Data.Sqlite`);
- MetadataExtractor;
- OpenCvSharp 4.13;
- локальные YuNet/SFace для лиц через OpenCV DNN.

Целевая сборка: Windows 10/11 x64, self-contained, **один `PhotoArchiveManager.exe`**. Пользователь собирает через `BUILD_ON_CLEAN_WINDOWS.bat`, в том числе на чистой Windows без заранее установленного .NET SDK.

Пользователь сам тестирует собранный EXE и присылает `build.log`/скриншоты. Если текущая версия не компилируется или падает — сначала исправлять её, а не уходить в новую функциональность.

### Предыдущий канон: 1.14.4

1.14.4 — усиление физического переноса Organization/Quarantine поверх 1.14.3 без изменения SQLite schema/Quality-кэша.

- Organization проверяет полный SHA-256 уже у конечного файла; cross-volume source tombstone удаляется только после этой проверки. Совпадение SHA-256 гарантирует побайтовое сохранение встроенных EXIF/IPTC/XMP/ICC.
- При Organization LastWriteTime сохраняется исходным. CreationTime берётся из встроенной EXIF capture-date, если она есть; иначе сохраняется исходный CreationTime. При ручной каталоговой CaptureDate используется сохранённая AutoCaptureDate только с EXIF-источником; ручная дата сама CreationTime не переписывает.
- Файловые даты после записи перечитываются и проверяются; FAT-округление до 2 секунд допускается с runtime WARN. Files.CreationUtcTicks/LastWriteUtcTicks и валидные cache-signature ticks синхронизируются с фактическим конечным файлом без пересчёта, поскольку содержимое подтверждено SHA-256. Undo синхронизирует их обратно с фактическим restored-файлом.
- Quarantine/Undo также проверяет SHA-256 конечного пути и явно восстанавливает/проверяет исходные CreationTime/LastWriteTime. SQLite schema `user_version=19`, Quality Score v3.3 / `QualityAlgorithmVersion=6`.

## Критические инварианты безопасности — НЕ ЛОМАТЬ

- При анализе оригиналы только читаются.
- Никаких автоматических необратимых удалений.
- Точный дубль доказан только после полного SHA-256.
- Визуальная похожесть не является доказательством дубля.
- Карантинный перенос проверяется SHA-256.
- Между дисками: `copy → SHA-256 verify → delete source`.
- Undo не перезаписывает существующий файл по старому пути.
- Обычный permanent delete разрешён только для уже карантинного файла и требует dangerous mode, двух подтверждений и повторного SHA-256. Отдельное исключение 1.14.1 — вручную включаемый direct-delete только для доказанных exact-SHA-256 дублей: keeper/candidate заново проверяются, минимум одна копия сохраняется, Undo отсутствует.
- Никакой автоматической очистки карантина.
- Люди/группы/лица меняют только БД, а не оригиналы.
- Ручная дата меняет только SQLite; EXIF/mtime/оригинал не переписываются.
- Ручная дата переживает повторный scan; автоматическая дата хранится отдельно для отката.
- Перенос фото между событиями меняет только `EventFiles/Events` в SQLite.
- Ручная правка событий должна защищаться от последующей автоматической перестройки.
- Физическая организация сначала только Preview.
- Никогда не перезаписывать существующий destination-файл.

## Важные технические особенности

- OpenCvSharp4 `4.13.0.20260627`: managed API отличается от общей документации.
- SFace запускается через DNN `Net`; выравнивание по 5 landmarks YuNet реализовано внутри PAM.
- У этой версии `FaceDetectorYN` не следует рассчитывать на `SetInputSize`; детектор создаётся сразу под нужный размер.
- Не менять major OpenCvSharp без необходимости.
- `OpenCvSharp.Analyzers` исключён, поскольку раньше давал `CS9057`; runtime OpenCV при этом используется нормально.
- Face index algorithm version = 2. Запросы людей должны использовать текущую версию индекса.
- Автогруппировка людей сохраняет именованные группы и пересобирает только неназванные автоматические.
- Автособытия используют только EXIF capture time или явную ручную дату. Filesystem fallback не считается достоверной датой события.
- SQLite foreign keys должны быть включены для каждого connection.
- WAL используется без `Cache=Shared`.
- В проекте есть bounded LRU миниатюр и параллельные независимые read-only refresh-запросы; не ломать это без причины.
