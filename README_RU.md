# Photo Archive Manager 1.15.7

Локальный Windows-каталог для большого семейного фотоархива. Основная цель проекта — безопасно разобрать многолетний архив: найти точные и визуальные дубли, серии, людей и события, восстановить каталоговые даты старых снимков, удобно просматривать архив по хронологии и затем при необходимости аккуратно разложить его физически.

Сборка ориентирована на Windows 10/11 x64 и публикуется как один self-contained `PhotoArchiveManager.exe`.

Для передачи проекта в новый чат/Codex см. `START_NEW_CHAT_OR_CODEX_RU.txt`, `HANDOFF_NEW_CHAT_OR_CODEX_RU.md` и `NEXT_STAGE.txt`.

## Новое в 1.15.5 — глобальные отметки карантина по всей вкладке

- Исправлен реальный баг «Похожие / копии»: галочки `в карантин`, поставленные в нескольких визуальных группах, раньше сохранялись в интерфейсе, но команда выполнения брала кандидатов только из `SelectedVisualDuplicateGroup`. Теперь итоговое превью и физический карантин собирают **все отмеченные файлы из всех групп текущей вкладки**.
- То же исправление применено к «Сериям»: `В карантин все отмеченные` обрабатывает отметки во всех сериях, а не только в открытой. Перед первым переносом PAM проверяет каждую затронутую группу/серию и полностью отменяет запуск, если где-то отмечены все кадры и не остаётся keeper.
- Итоговое подтверждение теперь явно показывает количество затронутых групп/серий, общее число отмеченных файлов и общий объём. Дополнительно проверяется невозможная ситуация, когда один `FileId` оказался отмечен сразу в нескольких группах одного анализа.
- Отметки карантина теперь сохраняются **по FileId по всей вкладке** при `Из кэша`, переоценке качества и повторной сборке групп. Раньше reload сохранял состояние только текущей открытой группы и мог тихо потерять уже сделанный разбор других групп.
- `Снять ВСЕ галочки во вкладке` теперь действительно очищает все группы/серии, что соответствует подписи. При частичной ошибке физической операции отметки на не обработанных файлах сохраняются после перегруппировки для повторной попытки.
- После реального карантина из «Похожие / копии» и «Серий» зависимые вычисленные представления инвалидируются единообразно, чтобы другие вкладки не продолжали показывать уже перемещённые файлы; текущая вкладка при этом сохраняется до перегруппировки для переноса оставшихся отметок.
- SQLite schema остаётся **`user_version=20`**, Quality Score v3.3 / `QualityAlgorithmVersion=6`; формат существующей `Data/archive.db` не меняется.

## Новое в 1.15.4 — единый multi-select и drag&drop в рабочих разделах

- «Люди → лица» теперь работает пакетно: `Ctrl`/`Shift`/`Ctrl+A` выделяют несколько лиц; назначение другой группе, возврат в «Без группы» и исключение применяются ко всему выделению. Выделенные лица можно перетащить **одной пачкой** на другую группу людей; drop на «Без группы» возвращает всю пачку в ungrouped.
- Пакетные операции с лицами выполняются атомарно в SQLite: назначение/снятие принадлежности не оставляют половину пачки обработанной; массовое исключение создаёт **одну Undo-запись** на всё выделение.
- Несколько групп людей можно выделить и перетащить на целевую группу. Целевая группа сохраняет своё имя и обложку; все выбранные source-группы поглощаются одной транзакцией. Drop выбранных групп на «Без группы» выполняет их пакетное расформирование.
- Правый клик внутри уже существующего multi-select больше не схлопывает выделение не только у групп людей, но и в «Библиотеке», «Люди → лица» и «События → фото». При этом строка под правым кликом становится текущей для одиночных команд (просмотр/обложка и т. п.), а batch-команды всё равно получают полный набор; правый клик по невыделенной строке выбирает только её.
- `Ctrl+A` явно поддержан для основных multi-select списков: Библиотека, группы людей, лица и фотографии события. Drag начинается со снимка/лица/группы внутри текущего выделения и переносит **всю** выбранную пачку.
- После переноса лиц или фотографий события PAM остаётся в исходной группе/событии, пока там ещё что-то осталось. Если источник опустел и исчез, выбирается именно цель переноса.
- Разделы, где multi-select был бы двусмысленным или опасным, намеренно не превращены в drag&drop-редактор: в exact-дублях выбирается один keeper; в «Похожие / копии» и «Серии» массовое действие задаётся галками `в карантин`; «Хронология» остаётся просмотром; «Организация» использует свой batch-preview/selection workflow.
- SQLite schema остаётся **`user_version=20`**, Quality Score v3.3 / `QualityAlgorithmVersion=6`; физические файлы при этих каталоговых операциях не изменяются.
- Build-имена больше не содержат вручную забитую версию: `BUILD_ON_CLEAN_WINDOWS.bat` и `bootstrap_windows.ps1` читают `VERSION.txt`; перед publish PowerShell проверяет совпадение `<Version>` в `.csproj`, а self-test обязан вернуть точно `Version=<VERSION.txt>`. Заголовки окон и «О программе» берут runtime-версию из assembly metadata через `AppPaths.AppVersion`.

## Новое в 1.15.3 — release-hardening перед финальной сборкой

- Убраны оставшиеся runtime-хвосты версии 1.14.8: стартовый лог, JSON-экспорт каталога, OpenCV diagnostics и portable self-test теперь берут номер из metadata самой сборки через `AppPaths.AppVersion`, поэтому кодовая версия больше не расходится с EXE.

- Release-компиляция настроена с `TreatWarningsAsErrors=true`: предупреждения C# теперь ломают сборку вместо того, чтобы попасть в релиз незамеченными.

## Новое в 1.15.2 — drag&drop объединение событий

- В дереве «События» можно перетащить **само событие на другое событие**. После подтверждения исходное событие поглощается целевым; фотографии физически не перемещаются и не изменяются.
- Имя итогового события всегда берётся у **цели**, на которую перетащили. Обложка цели имеет приоритет; если у цели обложки нет, может использоваться обложка исходного события.
- После объединения PAM выбирает целевое событие. Заметки не теряются: при наличии текста у обеих сторон они объединяются.
- Обычная команда «Объединить…» приведена к той же семантике: выбирается событие-цель, и его имя сохраняется; отдельное поле итогового имени убрано как двусмысленное.
- Перетаскивание отдельных фото между событиями сохранено и работает отдельно от drag&drop самих событий.
- Любое ручное объединение/перенос фото инвалидирует старый Preview организации, потому что состав событий изменился.
- SQLite schema остаётся **`user_version=20`**; миграция не требуется.

## Новое в 1.14.9 — источник можно закрыть с активным карантином

- Активные файлы в карантине больше **не блокируют удаление/закрытие источника из PAM**. Карантин — завершённое безопасное состояние, а не незаконченная операция.
- При варианте «убрать источник и забыть активные записи/анализы» обычные записи каталога очищаются, а минимальные audit-строки и Actions для Quarantine/Undo сохраняются скрытыми.
- Undo карантина для уже закрытого источника физически возвращает файл по исходному пути, но **не делает старый источник снова активной библиотекой**: запись остаётся `IsMissing=1`, пока пользователь снова не добавит этот источник.
- Если источник всё ещё активен, Undo работает как раньше и сразу возвращает запись в активный каталог.
- SQLite schema остаётся `user_version=20`; миграция не требуется.

## Новое в 1.14.6 — глубокий аудит safety/миграций

- Проведён повторный аудит изменений 1.11.0–1.14.5 с упором на физические операции, exact-дубли, Undo, даты/метаданные, SQLite-миграции и batch-действия «Людей».
- SQLite schema повышена до **`user_version=20`**. Журналы `OrganizationMoves` и `Actions` теперь сохраняют исходные `CreationTimeUtc`/`LastWriteTimeUtc`, поэтому Undo восстанавливает именно файловые даты до операции, а не даты уже перемещённого файла.
- Organization больше не считает «доверенной» формально trusted, но неразбираемую дату; auto-selection требует реально разобранную дату. Подсказка Preview показывает фактически выбранную схему раскладки.
- После физического move критические DB commit/rollback доводятся с `CancellationToken.None`: Stop не может оборвать программу в промежутке «файл уже перенесён, журнал ещё не согласован». Cross-volume служебные tombstone-файлы имеют внутреннее расширение `.pamtmp`, а scanner игнорирует только зарезервированные PAM temporary patterns.
- Organization и Undo дополнительно запрещают работу через junction/symlink внутри записанных корней. Undo карантина теперь также проверяет, что `OriginalPath` находится внутри сохранённого исходного source-root и не проходит через reparse point.
- Exact quarantine удерживает проверенный keeper открытым на весь batch, как и direct-delete.
- Исправлена идентичность каталога после карантина/direct-delete: неактивный `Files.FullPath` отсоединяется от старого физического пути, поэтому новый файл, появившийся позже по тому же имени, получает новый FileId и не наследует `IsQuarantined/IsDeleted`. Миграция сделана повторяемой/идемпотентной.
- People review для multi-select теперь записывается одной SQLite-транзакцией, без состояния «часть выделения обработана, часть нет».
- Portable self-test разделяет проверки миграций **18→19** и **19→20**, проверяет новые journal columns и повторное использование физического пути после inactive-record migration.
- `BUILD_ON_CLEAN_WINDOWS.bat` сохранён без UTF-8 BOM; исправлен актуальный путь результата сборки. Quality Score остаётся v3.3 / `QualityAlgorithmVersion=6`.

## Новое в 1.14.5 — множественный выбор групп людей

## Новое в 1.14.4 — контроль метаданных и файловых дат после переноса

- Organization теперь проверяет **полный SHA-256 именно конечного файла по окончательному пути**. При cross-volume переносе исходный tombstone удаляется только после этой финальной проверки; совпадение полного SHA-256 гарантирует побайтовое сохранение встроенных EXIF/IPTC/XMP/ICC и прочего содержимого файла.
- При физической организации **дата изменения (LastWriteTime) сохраняется исходной**. **Дата создания (CreationTime)** нового файла берётся из встроенной EXIF даты съёмки (`DateTimeOriginal` / другой EXIF capture-date, уже выбранный PAM), если она есть; иначе сохраняется исходная дата создания файла. Если пользователь вручную исправил каталоговую CaptureDate, PAM всё равно берёт CreationTime из сохранённой scanner AutoCaptureDate только когда её источник EXIF; ручная дата каталога не выдаётся за встроенную EXIF.
- После установки CreationTime/LastWriteTime PAM перечитывает их с диска и проверяет. Допускается только системное округление до 2 секунд на файловых системах FAT-family; такое округление пишется в лог.
- Каталог `Files` синхронизируется с фактическими `CreationUtcTicks`/`LastWriteUtcTicks` конечного файла. Так как содержимое подтверждено SHA-256, связанные hash/pHash/Quality/Face/GPS/Semantic signature-ticks безопасно переносятся на фактический LastWrite без лишнего пересчёта кэшей. Undo делает ту же синхронизацию.
- Quarantine/Undo также теперь проверяет SHA-256 **конечного** quarantine/restore-файла и после переноса явно восстанавливает/проверяет исходные CreationTime и LastWriteTime. SQLite schema остаётся `user_version=19`, Quality Score v3.3 / `QualityAlgorithmVersion=6`.

## Новое в 1.9.0 — Quality Score v3.2: локальная проверка вероятно закрытых глаз

- Добавлены кэш-поля `EyeOpennessScore`, `ClosedEyeCount`, `BlinkPenalty`; JSON/CSV экспорт и экран сравнения показывают эти данные. `QualityAlgorithmVersion=5`, поэтому старые Quality v3.1 автоматически пересчитаются.
- SQLite schema повышена до **`user_version=18`** только добавлением новых колонок; существующая `Data/archive.db` мигрирует на месте, оригинальные фотографии не изменяются.
- Новых NuGet-пакетов и новых ONNX-моделей нет. Если позже реальные серии покажут, что эвристика даёт слишком много `Unknown` или ложных срабатываний, калибруются пороги, а не маскируются сомнительные случаи жёстким штрафом.

## Новое в 1.8.1 — Quality Score v3.1, полностью локальная оценка качества

- Quality Score v3 повторно проверен и уточнён до **v3.1**. Во время анализа нет интернет-запросов, облачных API или отправки фотографий наружу: используются только локальный OpenCV и уже встроенный в EXE YuNet. Новые NuGet-пакеты и новые внешние AI-модели для Quality Score не добавлялись.
- Резкость больше не определяется одной variance of Laplacian. v3 анализирует **edge acutance в двух масштабах** и силу реальных сильных границ, поэтому шум матрицы заметно труднее принять за полезную резкость, а гладкий малодетальный сюжет не объявляется автоматически «мыльным».
- Оценка смаза объединяет многомасштабную резкость, контраст сильных границ и их направленность; это лучше отличает расфокус/смаз движения от просто низкоконтрастной сцены.
- Добавлена отдельная локальная оценка **высокочастотного шума** по плоским областям кадра.
- Экспозиция больше не требует средней яркости около 127.5. Используются перцентили гистограммы и реальный клиппинг теней/светов, поэтому снег, ночь, закат и силуэт не штрафуются только за то, что сцена объективно светлая или тёмная.
- Добавлен отдельный **тональный диапазон/контраст** по P05–P95/P01–P99 и локальному контрасту.
- Для JPEG вместо приблизительного `bytes/pixel` читаются реальные **DQT-таблицы квантования** из заголовка файла и оценивается эквивалентное JPEG quality. Сложность сюжета (трава, небо, волосы) больше не должна сама по себе менять балл компрессии.
- Разрешение/мегапиксели вынесены из общего технического Quality Score. Показатель «сохранность» остаётся отдельным сигналом и tie-breaker, но старый хороший 6 МП оригинал не проигрывает плохому 24 МП кадру только из-за размера.
- Лицевая часть Quality Score переведена со старых Haar Cascade на **YuNet**. Для основных лиц учитываются локальная детализация, геометрия/поза, размер/обрезание и уверенность детектора. В групповом фото отдельно учитывается **худшее основное лицо**, чтобы один плохой человек не растворялся в среднем по группе.
- Показатель глаз в v3 означает **детализацию/видимость области глаз** по landmarks YuNet. PAM намеренно не называет это детектором моргания: надёжного `eyes open/closed` классификатора в 1.8.1 нет.
- В «Сериях» и визуальных дублях при почти равном Quality Score дополнительным tie-breaker становится худшее основное лицо, затем резкость и сохранность разрешения.
- Внутренняя версия quality-cache повышена до `QualityAlgorithmVersion=4`: автоматически пересчитываются и старый v2, и оценки 1.8.0/v3, чтобы новая лицевая логика не смешивалась со старой. Оригинальные фото при этом не изменяются.
- Ошибка YuNet/локальной модели больше не сохраняется как «успешная техническая оценка без лиц»: такая запись остаётся ошибкой и будет повторно рассчитана после исправления runtime/model-проблемы.
- YuNet получает кадр до 1800 px по длинной стороне, технические метрики сохраняют прежнюю калибровку 1200 px. Мелкие, но значимые лица в групповых фото теряются реже.
- Убрано принудительное минимальное 5% влияние любого найденного лица. Вес начинается с нуля и растёт с реальной значимостью; group bonus считается только по основным лицам.
- Все восемь EXIF Orientation (включая зеркальные 2/4/5/7) теперь единообразно применяются в Quality, thumbnails, viewer и perceptual hash. Старые perceptual hashes для зеркальных ориентаций одноразово инвалидируются миграцией.
- Локальные YuNet/SFace в `Data\Models` при первом использовании теперь проверяются SHA-256/размером против embedded-копии; устаревшая или повреждённая модель автоматически заменяется. Неиспользуемые Haar Cascade удалены из сборочной цепочки.
- SQLite schema = **`user_version=17`**. Поля Quality v3 были добавлены ещё схемой 16; схема 17 добавляет `PerceptualHashAlgorithmVersion`, чтобы не смешивать старые hashes с новым bounded-decode/EXIF-алгоритмом. Существующая `Data/archive.db` мигрирует на месте и сохраняется.
- JSON/CSV экспорт дополнен компонентами Quality Score v3.1.
- Ограничение остаётся честно зафиксированным: декодирование HEIC/HEIF/AVIF/части WEBP идёт через Windows WIC и может зависеть от установленного системного кодека. JPG/PNG/BMP/TIFF не имеют этой внешней codec-зависимости. Никакого скачивания кодеков во время анализа PAM не выполняет.

- дата Windows `fallback` по-прежнему не считается доверенной автоматически.

Если дата меняется у фотографии, которая входила в автоматическое событие, PAM отвязывает только эту фотографию от автособытия и предлагает заново запустить анализ событий. Вручную закреплённые события не разрушаются.

Для совместимости со старой `Data\archive.db` миграция выполняется на месте: добавляются поля автоматически найденной даты, существующие даты копируются в них. Удалять `Data` при обновлении не нужно.

## Сохранено из 1.0.2 — удаление группы на вкладке «Люди»

После автоматической группировки не нужно убирать лица из ненужной группы по одному. Для выбранной группы есть команда:

`Удалить / расформировать всю группу`

Она:

- одним действием отвязывает от группы все найденные лица;
- удаляет саму запись группы/имя из локального каталога PAM;
- возвращает лица в раздел `Без группы`;
- **не удаляет, не перемещает и не изменяет файлы фотографий**;
- требует явного подтверждения;
- для именованной группы отдельно предупреждает, что имя группы будет забыто.

Это пакетный аналог команды `Убрать это лицо из группы`. Если после этого снова запустить автоматическую группировку, неназванные лица могут быть сгруппированы заново.

## Безопасная физическая организация архива

Во вкладке **«Организация»** PAM умеет как быстро разложить архив только по датам, так и выполнить полную раскладку с событиями.

1. Выберите отдельную корневую папку нового архива.
2. Выберите режим:
   - `Быстрая: только год` → `2024\фото.jpg`;
   - `Быстрая: год → месяц` → `2024\08 — август\фото.jpg`;
   - `Быстрая: год → месяц → день` → `2024\08 — август\18\фото.jpg`;
   - `Полная: год → месяц/событие` — прежняя глубокая организация с событиями.
3. Нажмите **«Построить Preview»**. PAM покажет для каждого файла `БЫЛО → СТАНЕТ` и ничего не изменит.
4. По умолчанию к перемещению отмечаются только файлы с доверенной датой: EXIF или ручной датой каталога. Фото, где известна только файловая дата Windows, автоматически не отмечаются; fallback включается отдельно.
5. В быстрых режимах исходное имя файла сохраняется. Настройки «Дата в имени файла» и «Имена людей в имени файла» работают только в полном режиме.
6. В полном режиме в имя папки попадает только осмысленное вручную названное событие; служебное автоназвание из одних дат/времени не используется.
7. Перед реальным выполнением требуется два подтверждения. Каждый файл проверяется SHA-256; существующие файлы никогда не перезаписываются.
8. Между дисками применяется `copy → SHA-256 verify → delete source`. Каждое успешное перемещение записывается в журнал и имеет Undo.
9. После успешной быстрой раскладки PAM спрашивает, использовать ли получившийся корень как основу дальнейшей сортировки. При ответе «Да» выбирается полный режим и строится новый Preview в том же корне — **без автоматического второго перемещения**.

Пример быстрой структуры по месяцам:

```text
Archive
├── 2014
│   ├── 07 — июль
│   └── 08 — август
├── 2015
│   └── ...
└── Без достоверной даты
```

Пример полной структуры:

```text
Archive
├── 2014
│   ├── июл
│   └── авг — Отпуск в Крыму
├── 2015
│   └── ...
└── Без достоверной даты
```

При включённых настройках имени в полном режиме целевой файл получает календарную дату без времени и подтверждённых людей, например `2014-08-03_IMG_1234 — Маша, Олег.JPG`. Исходное имя `IMG_1234` сохраняется.

## Управление источниками

В библиотеке доступны:

- `+ Добавить папку`;
- `− Убрать источник` — сам каталог и файлы на диске не удаляются;
- `⇄ Заменить путь` — если диск/папка переехали, PAM переписывает пути своей БД и сохраняет рассчитанные анализы.

## Критические правила безопасности

- анализ оригиналов выполняется в режиме чтения;
- ручная коррекция даты меняет только SQLite-каталог;
- никакой существующий файл не перезаписывается;
- точные дубли по умолчанию отправляются в карантин после повторной SHA-256 проверки; вручную включаемый сессионный direct-delete допускается только для полных exact-SHA-256 дублей и также повторно проверяет keeper/candidates;
- визуальная похожесть сама по себе никогда не является основанием для удаления;
- обычное окончательное удаление возможно из карантина после отдельного dangerous mode и двух подтверждений; исключение — явно включённый на вкладке exact-дублей direct-delete, который не использует Undo и всегда требует подтверждения конкретной массовой операции;
- опасный режим сбрасывается при каждом запуске;
- автоматической очистки карантина нет;
- операции с группами людей меняют только SQLite-каталог, а не фото;
- ручные правки событий (имя, объединение, перенос фото) меняют только SQLite-каталог и закрепляют результат от автоматической перестройки.

## Сборка на «голой» Windows 10/11 x64

Распакуйте исходники и запустите:

```text
BUILD_ON_CLEAN_WINDOWS.bat
```

Скрипт сам загружает локальный .NET 8 SDK, NuGet-пакеты и необходимые модели.

Готовый EXE:

```text
BUILD_OUTPUT\PhotoArchiveManager_<версия из VERSION.txt>_win-x64\PhotoArchiveManager.exe
```

Каталог `Data` — пользовательская база и кэш. При обновлениях его нельзя без необходимости удалять: там находятся `archive.db`, результаты анализов, лица, события, карантин и журналы Undo. В существующей БД старые колонки избранного/рейтинга могут оставаться как нетронутые legacy-данные, но 1.11.0 ими не пользуется; свежая база эти колонки уже не создаёт.

## Перед массовой физической раскладкой

Сначала проверяйте «Организацию» на копии небольшой папки: preview → несколько перемещений → Undo → перенос между дисками. Только после этого применять к основному архиву.
